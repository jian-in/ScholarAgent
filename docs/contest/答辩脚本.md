# 答辩脚本

> 预计时长 5 分钟。每个数字后的【】内是仓库内可核验的来源；评委追问时
> 直接打开对应文件。

## 开场（30 秒）

各位评委好。ScholarAgent 是一个面向科研文献调研的透明智能体实验台。
"透明"是关键词：它不只给最终回答，而是把执行模式怎么选、轨迹怎么走、
成本花在哪、失败长什么样，全部留下来可复验。

【README 首屏「当前证据与边界」】

## 技术创新（1 分 40 秒）

第一，**从零实现的轻量框架**。ReAct 核心循环约 200 行
【`scholaragent/agent.py`】，运行时只有 4 个依赖【`requirements.txt`】，
不依赖 LangChain 这类编排封装，每个环节的行为都可审计。

第二，**可解释的三模式路由**。系统从任务文字提取版本化特征，在
ReAct、Plan、Team 三种模式间自动选择。路由不是黑盒打分，而是输出
人话理由。规则路由在固定 36 题上与复杂度标签全部一致，这个结论
零模型调用即可复验【README「成本感知自适应路由」节的命令】。

第三，**执行级指标与产物追踪**。每次运行记录真实耗时、LLM 调用、
工具调用和 token；API 没返回 token 就记 None，绝不估算
【`scholaragent/metrics.py`】。论文、笔记、记忆产物按运行归档。

第四，**失败可见**。学习路由的策略文件缺失或损坏时，系统打印原因并
安全回退到规则路由，有专门测试保护【`tests/test_cost_aware_routing.py`】。

## 场景落地（1 分 30 秒）

主证据是一个真实案例：让三种模式各自调研 ReAct 原论文，arXiv 编号
2210.03629【`docs/case-study.md`】。

- Plan 模式得 0.945 分：它先拆计划再执行，回答里有逐字引文和页号；
- Team 模式 0.885 分：检索员、精读员、写作员流水线，还对比了后续工作；
- ReAct 模式只有 0.175 分——33 页论文耗尽了 15 步预算，**没有产出回答**。
  这次失败被完整保留在证据包里，没有重跑美化。

这组对比正说明为什么要做模式路由：任务形态不同，合适的执行结构不同。
现场演示走五分钟黄金路径：输入任务 → 看路由理由 → 看轨迹 → 看产物 →
看指标【`docs/demo-guide.md`】，网络故障时切换离线证据包兜底。

## 开源治理与长期发展（1 分钟）

治理上：MIT 许可证，贡献指南、安全策略、行为准则、维护说明齐备；
Issue / PR 模板和双系统 CI 就绪【`.github/`】。特别的一点是把**发布纪律
写进了测试**——`tests/test_public_release.py` 会自动拦截私人信息、
运行产物和敏感措辞，共 8 道发布闸门。

长期上：季度路线图把比赛线和研究线分开【`docs/ROADMAP.md`】——短期做
打包发布和插件接口，中期是研究线：完成 54 题完整校准、训练学习路由、
留出集五策略对比。

## 诚实边界（20 秒，主动说）

最后主动说明：目前 29/54 条校准观测只用于成本诊断，学习路由的正式
结论尚未产出；案例评分是作者初步自评。这些边界都写在 README 首屏，

## 预备问答

- **问：和 LangChain 生态比优势是什么？**
  答：不是比功能多，而是比可解释和可审计——路由理由、执行指标、失败
  记录都是一等公民，且全部可离线复验【README「与同类工具的差异」表】。
- **问：36/36 一致说明了什么？**
  答：只说明规则路由与人工预设的复杂度标签一致，是工程正确性验证，
  不代表回答质量。
- **问：学习路由什么时候有结论？**
  答：需要完成 54 题校准的人工评分和留出集实验，计划在路线图研究线
  2026 年内完成【`docs/ROADMAP.md` 研究路线节】。
- **问：和 Claude / GLM 这类云端智能体助手相比，这个项目的意义是什么？**
  答：不比“谁更聪明”——纯看完成调研的质量，前沿云端模型更强，本项目是
  模型无关的框架，这一点在 README 边界声明里如实承认【README 首屏】。
  它提供的是云端产品给不了的五件事：可审计的编排（约 200 行核心循环 +
  带特征和理由的路由决策）；可控可测的成本（执行级指标、上下文压缩、
  按任务复杂度选更便宜的模式）；数据主权（论文、笔记、长期记忆全是
  本地文件，未发表材料不出机器）；可复现的评测框架（固定任务集、三模式
  消融、评分与原始运行分离）；以及完整本地运行能力（Ollama 零成本、
  可离线）。本项目最新版本恰好示范了两者如何结合：双模型分工——云端
  负责检索与工具决策，本地负责总结降本【README「本地工作台」节】。
  一句话：哈勃望远镜再好，天文学家仍需要一台自己能校准、能解释误差的
  观测设备。
